# AI 产品落地面试问答：从“能做”到“值得上线”

> 这份文档用于面试追问。核心观点：AI 功能不是用户说要就做，也不是模型变强就能上线。真正的产品落地要同时判断场景价值、模型能力、数据条件、链路可控性、成本收益与上线标准。

---

## Q1：怎么判断一个 AI 功能该不该开发落地？

### 新手误区

“用户有需求，直接做就好了。”

### 专业判断框架

AI 功能是否值得开发，要从 6 个维度判断：

| 维度 | 关键问题 |
|------|----------|
| 用户价值 | 是否解决高频/高痛/高价值场景，而不是锦上添花？ |
| 模型能力 | 当前模型是否稳定支撑该场景？是否容易幻觉或误判？ |
| 数据条件 | 是否有合规、可用、可更新的业务数据？ |
| 链路适配 | 适合 RAG、工具调用、Agent，还是规则 + LLM？ |
| 成本收益 | 开发、推理、维护成本是否匹配业务收益？ |
| 迭代节奏 | 是否适合当前产品阶段，还是应先做轻量验证？ |

### 和本项目的映射

智衡 AI Radar 没有直接做“AI 自动排名”，而是先做：
- 结构化工具目录
- 来源报告
- 七维评分契约
- 对比弹窗

原因是“自动生成全球排名”虽然看起来酷，但落地风险高、可信度低；而“可追溯选型看板”更符合 PM/工程师的真实决策场景。

### 面试回答模板

我不会只因为用户说想要就直接做。我的判断顺序是：先看场景是否高价值，再看模型能力和数据条件是否支撑，然后判断应该用规则、RAG、工具调用还是 Agent，最后评估成本收益和迭代节奏。很多 AI 功能不是做不出来，而是上线后没有稳定价值。

## Q2：大模型上线后效果差、幻觉多，你怎么处理？

### 新手误区

“换更强模型，找算法优化。”

### 专业排查顺序

不要先换模型，先定位问题发生在哪一层：

1. **输入层**：用户问题是否过宽、歧义大、缺少上下文？
2. **知识层**：文档质量是否差、过期、重复、冲突？
3. **切片层**：chunk 是否过长/过短，语义是否断裂？
4. **检索层**：Embedding 是否匹配不准，召回是否缺失？
5. **重排层**：topK 是否过多/过少，是否需要 rerank？
6. **Prompt 层**：是否明确禁止编造、要求引用来源？
7. **工具层**：工具调用参数、权限、失败兜底是否正常？
8. **上下文层**：是否上下文溢出、多轮状态丢失？
9. **模型层**：前面都确认后，才考虑模型升级。

### 和本项目的映射

智衡 AI Radar 的处理策略是：
- 分数不由 RSS 自动改写，避免“模型看了新闻就乱改分”
- 每条工具保留 `sources` 与 `scoreEvidence`
- 来源报告页展示抓取状态与数据资产路径
- 方法论页说明“只更 changelog，不自动改分”

### 面试回答模板

我会先把 badcase 分类，不会直接换模型。重点看是检索没召回、切片不合理、Prompt 没约束、工具调用失败，还是上下文溢出。优先通过检索、重排、Prompt、知识库质控和降级策略解决，最后才考虑模型升级。

## Q3：平时项目评测、问题排查用什么工具和方法？

### 新手误区

“本地跑一遍，看效果差不多。”

### 专业方法

AI 项目评测要同时有链路追踪、批量 badcase、量化指标和版本对照。

| 方法 | 用途 |
|------|------|
| LangSmith / Tracing | 看清每一步输入、检索、工具调用、输出 |
| Badcase 集 | 收集失败样本，按场景聚类 |
| 批量评测 | 对比准确率、召回率、幻觉率 |
| Prompt A/B | 比较不同提示词版本 |
| Chunk A/B | 比较切片大小、重叠、结构化策略 |
| Rerank 对照 | 验证重排是否提升相关性 |
| 人工审核集 | 保留关键场景的黄金样本 |

### 和本项目的映射

当前项目是 Web 看板，不是问答 RAG，但依然保留了评测思路：
- `live-fetch-report.json` 记录每次抓取结果
- `data-contract.md` 定义数据契约
- `验收清单.md` 定义功能验收
- `05-test-and-qa-report.md` 定义测试范围与用例

### 面试回答模板

我不会凭感觉判断模型效果。我会先建立 badcase 集和黄金样本，再用链路追踪看问题发生在哪一层，同时做 Prompt、检索、切片、重排的版本对照。上线前看量化指标，而不是只看几条 demo。

## Q4：怎么判定你的大模型项目达到上线标准？

### 新手误区

“测试没报错，准确率看着还行。”

### 专业上线标准

AI 功能上线至少要满足：

| 标准 | 说明 |
|------|------|
| 核心场景效果达标 | 主路径准确率/召回率/满意度达到阈值 |
| 幻觉率可控 | 关键场景不能编造事实或违规建议 |
| 延迟可接受 | 首 token、流式响应、总耗时可控 |
| 兜底策略完整 | 无答案、低置信、工具失败时可降级 |
| 多轮上下文稳定 | 不丢状态、不错误继承上下文 |
| 数据合规 | 用户数据、业务数据、日志留存合规 |
| 灰度验证 | 小流量上线，观察指标后再放量 |

### 和本项目的映射

智衡 AI Radar 的上线判断包括：
- `npm run build` 通过
- 日更脚本可执行
- 单路公开源失败不影响旧快照
- 页面具备 fresh/stale/missing 状态
- 来源报告能解释数据从哪来
- 对比结论有证据与风险提示

### 面试回答模板

能跑不等于能上线。我会看核心场景效果、幻觉率、延迟、兜底、多轮稳定性、数据合规和灰度结果。特别是 AI 功能，必须明确低置信和失败时怎么处理，否则上线后风险很高。

## Q5：产品需求和技术落地冲突、场景复杂度太高怎么办？

### 新手误区

“听产品的，或者听组长的。”

### 专业处理方式

把冲突拆成“目标、约束、替代方案、阶段路径”：

1. 先还原产品核心诉求，而不是争论方案。
2. 明确模型能力边界和数据限制。
3. 按风险拆分场景：
   - 可直接做：低风险、高确定性
   - 降级做：先规则/模板/人工审核
   - 暂不做：缺数据、不可控、收益低
4. 给出 MVP 与后续演进路径。
5. 用评测结果和成本估算对齐决策。

### 和本项目的映射

项目中没有追求“一键智能排名所有 AI 工具”，而是拆成：
- 先做结构化目录
- 再做可追溯来源
- 再做七维对比
- 最后做智能弹窗与建议

这就是把复杂 AI 判断降级为可控产品链路。

### 面试回答模板

我不会简单说做或不做，而是先明确业务想解决什么问题，再结合模型能力、数据条件和成本拆方案。能轻量化的先 MVP，风险高的先降级或人工审核，伪需求就用数据解释为什么不做。

---

## 总结：AI 功能落地的 5 句话

1. 用户需求只是起点，不是开发指令。
2. 模型能力、数据条件和链路可控性决定能否落地。
3. 幻觉问题先查链路，再考虑换模型。
4. AI 项目上线看指标、兜底、合规和灰度，不看 demo 感觉。
5. 产品与技术冲突时，用 MVP、降级和评测数据对齐。

## 可直接用于智衡项目的收束回答

智衡 AI Radar 的设计思路就是把这些原则产品化：我没有做不可解释的“AI 排名”，而是把工具事实、来源等级、七维评分、日更报告和对比结论拆开。这样既能展示 AI 选型能力，也能让每个判断回到数据和来源，而不是模型随口生成。
