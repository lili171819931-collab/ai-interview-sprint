# AI 产品经理视角：从想法到可落地产品

## 1. AI PM 在本项目中的核心判断

智衡 AI Radar 的产品经理视角不是“做一个漂亮看板”，而是回答：

1. 用户为什么需要 AI 工具选型平台？
2. 哪些判断可以自动化，哪些必须人工维护？
3. 数据可信度如何呈现？
4. 如何避免 AI 结论误导用户？
5. 如何证明这个产品能长期迭代？

## 2. AI PM 工作框架

### Step 1：场景拆解

| 问题 | 本项目答案 |
|------|------------|
| 谁用？ | PM、工程师、企业采购/解决方案 |
| 什么时候用？ | 选型、竞品分析、采购前评估 |
| 替代什么？ | 人工搜索、Excel 对比、主观经验 |
| 核心价值？ | 更快形成可解释候选集与对比结论 |

### Step 2：AI 可行性判断

| 判断项 | 本项目处理 |
|--------|------------|
| 模型是否能自动评分？ | 不直接让模型评分，避免幻觉 |
| 数据是否合规可得？ | 仅用公开 RSS/Atom/Changelog |
| 是否适合 Agent？ | 本期不用复杂 Agent，先做可控日更管线 |
| 哪些自动化？ | changelog 抓取、来源报告、图像化对比 |
| 哪些人工维护？ | 工具基线、七维评分、证据口径 |

### Step 3：数据产品化

AI PM 需要把“信息”变成“产品资产”：

- `seed.ts`：人工维护事实底座
- `live-sources.ts`：公开源登记
- `daily-bundle.json`：页面事实源
- `live-fetch-report.json`：抓取审计报告
- `schema.ts`：数据契约

这让项目不是一次性页面，而是可持续更新的数据产品。

## 3. 需求取舍

| 需求 | 判断 | 结果 |
|------|------|------|
| 自动全网排名 | 高风险、低可信 | 不做 |
| 公开源日更 | 可控、有价值 | 做 |
| 七维评分 | 决策必要 | 做，但人工维护 |
| 对比弹窗 | 提升决策效率 | 做 |
| 用户账号/收藏 | 本期非核心 | 暂不做 |
| 导出 PDF | 有商业价值 | 放入下一阶段 |

## 4. AI PM 关注的指标

### 使用指标
- 目录搜索使用率
- 对比弹窗打开率
- 来源报告访问率
- 详情页停留与外链点击

### 数据指标
- 日更成功率
- stale 出现频次
- 来源覆盖率
- official 来源占比

### 业务指标
- 完成一次选型所需时间
- 候选工具收敛效率
- 报告复用次数
- 团队协作/采购评审使用次数

## 5. 上线策略

### MVP 验证
- 本地可运行
- 公开源可更新
- 对比路径可演示

### 小范围试用
- 面向 3 类用户：PM / 工程师 / 解决方案
- 收集：是否能更快形成候选集，是否信任评分，是否愿意复用报告

### 后续迭代
- 增加导出报告
- 增加场景模板
- 增加企业内部工具库
- 接入用户反馈与 badcase

## 6. AI PM 面试表达

### 一句话

我把 AI 工具选型从“主观经验”产品化成“可追溯的数据决策流程”。

### 三层表达

1. **产品层**：解决 PM/工程/采购的选型效率问题。
2. **AI 层**：没有盲目让模型自动评分，而是把 AI 放在可控的数据更新和辅助分析环节。
3. **工程层**：用数据契约、来源报告、降级策略和构建验收保证可落地。

### 可复述话术

> 作为 AI 产品经理，我最关注的不是“能不能用大模型做”，而是这个功能是否值得做、数据是否支撑、链路是否可控、上线后是否能持续产生价值。智衡的取舍是：不做黑盒排名，先做可信数据底座、结构化评分、来源审计和场景化对比。

## 7. 下一阶段产品路线

| 优先级 | 能力 | 价值 |
|--------|------|------|
| P1 | 对比报告导出 | 支持汇报与采购讨论 |
| P1 | 场景模板 | 降低新用户决策门槛 |
| P2 | 用户反馈/badcase | 优化评分与推荐 |
| P2 | 企业内部工具库 | 支持真实企业落地 |
| P3 | API 数据服务 | 延展为商业数据产品 |
