# PRD：票易报 · 发票报销 Web 平台

## 1. 背景与问题

- **用户是谁**
  1. 报销人：员工 / PM / 销售，每月要交票据，讨厌填表与反复驳回
  2. 审批人：主管，要在 1 屏内看懂金额、事由与风险
  3. 财务：要标准台账、可解释合规原因、可导出对账
- **现在怎么做（现状）**
  - Excel + 邮件/企微群传图
  - 或企业费控（SAP Concur / 每刻 / 合思等）但配置重、对中小团队过重
  - AI 聊天工具能「看看票」，但难形成可提交单据与审批闭环
- **痛点**
  1. 填表成本高：票种多、字段多、科目难选
  2. 驳回成本高：抬头不对、超标、缺材料，来回多轮
  3. 信任成本高：纯 AI 填金额易幻觉，财务不敢信
  4. 上下文断裂：对话式 Agent 与「可追溯单据系统」之间缺一层产品化
- **为什么现在做**
  - OCR/多模态识别成熟，但「规则引擎 + 可解释合规」才是财务愿意用的关键
  - 可作为面试作品：同时证明 B 端产品判断、AI 边界设计、可运行工程交付

## 2. 目标

- **业务目标**：把「散落发票」变成「财务愿意批的报销单」，降低一次通过时长与驳回率。
- **用户目标**：报销人 10 分钟内完成月度报销草稿；审批人 1 分钟看懂是否可批。
- **非目标（Won’t）**
  - ❌ 真对接税局验真（MVP 预留状态位 `unverified`）
  - ❌ 复杂组织权限 / 多级审批流引擎
  - ❌ 原生 App / 打款电子签 / 多租户计费
  - ❌ 境外多币种完整会计处理

## 3. 成功指标

| 指标 | 基线（手工） | MVP 目标 | 口径 |
|------|--------------|----------|------|
| 单次报销准备时长 | 30–60 min | ≤15 min | 从打开到提交草稿 |
| 首次提交驳回率 | 高（经验） | ↓30%+ | 驳回单 / 提交单 |
| 字段人工修改率 | — | 识别票 &lt;40% 字段被改 | 编辑字段数 / 总关键字段 |
| 审批理解时间 | 难量化 | ≤60s | 看摘要即可决策占比 |
| 金额幻觉事故 | 不可接受 | =0 | 系统金额与票面不一致且未标黄 |

详见 [`metrics.md`](metrics.md)。

## 4. 核心场景

### 主场景：批量月结报销（Mode B）
上传多票 → 自动抽取/归类/合规 → 处理待确认 → 提交 → 审批/导出

### 附属场景
1. **单票速报（A）**：能不能报 + 原因  
2. **差旅全包（C）**：行程一致性与缺票提示  
3. **招待审查（D）**：人均/对象/事前审批  
4. **驳回重提（F）**：带原因克隆修订稿  

## 5. 解决方案（产品策略）

**结构化事实层（规则） + 受限识别层（OCR/Mock） + 可解释合规层**

| 层 | 做什么 | 谁说了算 |
|----|--------|----------|
| 识别层 | 建议票面字段 | OCR/Mock，可被用户覆盖 |
| 事实层 | 金额勾稽、去重、汇总 | 纯规则，模型不可改数 |
| 合规层 | 可报/限报/拒报 + 原因 | 制度规则引擎 |
| 生成层 | 审批摘要文案 | 只能引用已校验 JSON |

关键原则：**AI 可以建议，账本必须可审计。**

## 6. 范围与版本

| 版本 | 内容 |
|------|------|
| MVP（已交付代码） | 登录、报销单、上传/手录、合规、提交审批、导出、种子数据 |
| v1.1 | 真实 OCR Provider 插拔、制度可编辑、验真 API |
| v1.2 | 企微/飞书通知、项目成本中心、审计看板 |

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| OCR 幻觉金额 | 置信度门禁；低置信不进可提交合计；金额用分存储 |
| 用户「怎么都要报过」 | 产品拒绝造假路径；只给合规建议 |
| 制度因公司而异 | Policy 可配置；通用基线显式声明来源 |
| 隐私 | 本地/私有化优先；日志脱敏；不默认外发 |
