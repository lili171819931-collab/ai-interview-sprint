# 用户旅程：票易报

## 角色地图

```
报销人 ──提交──► 审批人 ──通过/驳回──► 财务（导出/归档）
   ▲                 │
   └── Mode F 重提 ◄─┘
```

## 旅程 1：报销人月结（主路径）

| 步骤 | 用户目标 | 系统行为 | 成功标准 |
|------|----------|----------|----------|
| 1 登录 | 进入自己的单据 | Session Cookie | 看到工作台 |
| 2 新建 | 声明期间/事由/模式 | 创建 Claim | 进入详情页 |
| 3 上传 | 少填表 | Mock/OCR 抽取 | 列表出现票 |
| 4 复核 | 只处理异常 | 黄/红状态 + 原因 | 待确认可定位 |
| 5 提交 | 交给主管 | 锁定字段 | 状态=已提交 |
| 6 导出 | 备份/对账 | CSV + 摘要 | 文件可下载 |

**情绪曲线**：上传时轻松 → 看到红票略焦虑 → 原因可解释后可控 → 提交后安心。

## 旅程 2：审批人 1 分钟决策

1. 打开已提交单  
2. 先看四宫格金额（可提交/待确认/拒报/税）  
3. 读审批摘要  
4. 抽查 1–2 张高风险票  
5. 通过或驳回（必须填原因）  

## 旅程 3：驳回重提（Mode F）

1. 报销人看到驳回原因  
2. 一键生成修订草稿（克隆票据）  
3. 只改问题票  
4. 再次提交  
5. 审批人可对照「基于哪张驳回单」  

## 旅程 4：单票速问（Mode A）

「这张餐饮票能不能报？」→ 结论 + 依据 + 建议可报金额（不强制建完整月结单）。

## 空状态 / 失败态（必须有）

- 无报销单：引导新建  
- 无发票：引导上传或手录  
- 识别中：明确进度文案  
- 上传失败：可重试 + 可手录兜底  
- 已锁定单据：禁用编辑，提示状态  

## 设计原则（产品）

1. **异常优先**：先展示需要人处理的票，而不是平均信息墙  
2. **原因可读**：任何拒报必须能被财务和员工共同理解  
3. **可降级**：没有 OCR Key 也不能卡死主路径
