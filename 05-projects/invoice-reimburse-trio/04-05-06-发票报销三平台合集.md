## 2. 共享领域模型：一次建模

三平台共享同一套领域资产：类目体系、情景模式、合规思维链、制度基线。

### 2.1 费用类目体系（一级科目）

| 代码 | 名称 | 典型销售方/关键词 |
|------|------|-------------------|
| TRAVEL | 差旅费 | 酒店、铁路、航司、机票代理 |
| TRANSPORT | 市内交通 | 滴滴、地铁、公交、停车 |
| MEAL | 餐饮/餐补 | 餐饮店 + 加班/工作餐事由 |
| ENTERTAIN | 业务招待 | 餐饮/礼品 + 客户/宴请 |
| OFFICE | 办公用品 | 文具、打印、超市办公耗材 |
| COMM | 通讯网络 | 运营商、宽带、会议软件 |
| TRAINING | 培训学习 | 培训机构、考试费、课程 |
| WELFARE | 员工福利 | 体检、团建（按制度） |
| IT | 软件设备 | 云厂商、SaaS、电子市场 |
| MARKETING | 市场推广 | 广告、物料、展会 |
| LOGISTICS | 快递物流 | 顺丰、京东物流等 |
| MEDICAL | 医药体检 | 医院、体检中心（制度允许） |
| OTHER | 其他 | 必须备注，禁止滥用 |

### 2.2 票种字典

| 代码 | 名称 | 关键字段 |
|------|------|----------|
| VAT_SPECIAL | 增值税专用发票 | 购销方税号、税额 |
| VAT_NORMAL | 增值税普通发票 | 购买方、价税合计 |
| E_VAT | 电子发票 | PDF、发票号码 |
| DIGITAL_VAT | 数电票 | 20 位号码 |
| TRAIN | 火车票 | 乘车人、车次、日期 |
| FLIGHT | 机票行程单 | 乘机人、航班、舱位 |
| TAXI | 出租车票 | 时间、金额 |
| QUOTA | 定额发票 | 面额 |
| POS_RECEIPT | 小票收据 | 默认不可报 |
| OVERSEAS | 境外票据 | 汇率、翻译、特批 |

**归类启发式**：酒店/宾馆 → TRAVEL/酒店；铁路/航空 → TRAVEL/交通；餐饮+客户/宴请 → ENTERTAIN；餐饮+加班/工作餐且无客户 → MEAL；文具/办公耗材 → OFFICE；云/SaaS → IT；无法判断 → OTHER + low confidence + 强制确认。

**易混淆对**：招待 vs 餐补（是否有外部对象/商务目的）；差旅打车 vs 市内交通（是否落在出差行程日内）；团建 vs 招待（参与者是否主要为内部员工）；福利 vs 办公（是否个人消费属性更强）。

### 2.3 情景模式（Mode A–J）

| Mode | 名称 | 触发信号 | 额外动作 | 核心输出 |
|------|------|----------|----------|----------|
| A | 单票速报 | 1 张票 + 能不能报 | 快速结论 | 短报告 + 1 行明细 |
| B | 批量月结 | 文件夹/多票/本月报销 | 全流程报销包 | 台账 + 报告 + 归档 |
| C | 差旅全包 | 出差/拜访/驻场 | 行程轴、缺票检查 | 差旅单 + 时间线 |
| D | 招待审查 | 请客/宴请/招待 | 人均、对象、酒水 | 合规意见书 |
| E | 专票进项 | 抵扣/认证/进项税 | 分离专票、税号核对 | 进项汇总表 |
| F | 驳回重提 | 财务驳回/补充材料 | 变更对照 | 修订包 |
| G | 审计抽查 | 内审/异常/风险 | 重复拆票模式 | 风险工单 |
| H | 制度测算 | 能报多少/规则是什么 | 检索条款 + 举例 | 规则说明 |
| I | 境外多币种 | 外币/境外票 | 汇率折算 | 折算明细 + 特批草稿 |
| J | 垫付清算 | 个人垫付要回款 | 收款信息勾稽 | 应付确认单 |

**路由伪代码**：仅咨询规则 → H；提及驳回/重提 → F；审计/风险/重复报销 → G；境外/外币 → I；专票抵扣/进项 → E；招待/宴请 → D(+B)；出差/差旅 → C(+B)；单票判断 → A；否则 → B。
**组合示例**：月末市场部报销 `B+D`；销售出差 `B+C`；财务要进项清单 `E`；被拒后重交 `F`（保留原 ticket_id）。

### 2.4 合规思维链（CoT 流水线 Stage Gate）

```
Stage 0 意图解析   → 可提交 / 仅建议 / 仅归档；选 Mode；列 P0 缺口
Stage 1 材料盘点   → 统计文件；非票据进 _ignored；写 processing_manifest.json
Stage 2 票面抽取   → 标准字段 + confidence；low → 待确认队列
Stage 3 归一去重   → ① 发票号码 ② 销售方+日期+价税合计 ③ 文件哈希
Stage 4 归类       → primary/secondary/scene_tags；自检易混淆对
Stage 5 合规       → 抬头 → 日期期间 → 限额/人均/星级 → 事前审批
                    → 高风险消费 → 拆票/重复模式 → 金额税额勾稽
Stage 6 金额编排   → 可提交 / 拒报 / 进项税 分列
Stage 7 填单       → 审批摘要 / 明细台账 / 附件清单
Stage 8 归档       → 标准文件名；可提交/待确认/拒报分目录；原始备份
Stage 9 自检       → 加总一致？low 混入可提交？差旅缺票？摘要可 3 分钟审完？
Stage 10 交付      → 结论 + 待办 + 路径 + 下一步
```

**中断条件（任一成立不得宣称「可直接提交」）**：P0 信息缺失；可提交明细存在未解决 low 字段；金额勾稽失败未处理；需事前审批但缺失。

### 2.5 通用合规基线（Policy Template，可被企业制度覆盖）

**硬规则**
1. 购买方抬头必须与公司全称一致（可维护简称映射）；不一致 → non_compliant
2. `金额 + 税额 = 价税合计`（容差 0.01）；失败 → non_compliant
3. 相同发票号码只报销一次；其余 → duplicate
4. 小票/收据默认拒报，除非制度白名单
5. 未验真时标记 `unverified`，不得伪称已验真
6. 开票日期明显异常（未来日期等）→ conditional/non_compliant

**差旅默认限额（人民币/晚）**：一线（北上广深）600 / 新一线 450 / 其他 350。高铁默认二等座、机票默认经济舱，更高需职级规则或特批；出差用车须落在行程日期内。

**招待默认规则**：必须有事由 + 对象类型；人均上限 200（可配置），超出 → conditional；KTV/高尔夫等高风险娱乐 → 默认 non_compliant；金额 ≥ 1000 且无事前审批 → conditional。

**风险加分**：重复报销嫌疑 +30、抬头不一致 +20、周末大额餐饮无事由 +15、连号拆票嫌疑 +15、低置信度字段 +10、超标 +10；≥60 高风险，30–59 中，<30 低。

### 2.6 置信度门禁与硬约束

- high（≥0.90）：自动入可提交；mid（0.70–0.89）：入账但标黄；low（<0.70）：只进待确认，不进可提交合计
- 未真实查验时 `verification_status=unverified`，禁止伪称已验真
- 抬头不一致默认不可提交；小票/收据默认拒报
- 用户要求「无论如何报过」时拒绝造假，只给合规路径

## 3. 报销全流程 · 三平台实现对照

完整报销流程 = **收票 → 识票 → 归类 → 合规 → 填单 → 审批 → 交付**。三个平台都覆盖这条链路，但每步的实现形态不同：

| 流程步骤 | 04 WorkBuddy Skill | 05 票易报 Web | 06 票迹小程序 |
|----------|--------------------|---------------|---------------|
| ① 收票 | 扫描文件夹/图片/PDF/zip；过滤非票据 | 上传附件 + Mock OCR | 拍照 / 相册 / 邮箱 mock 同步 |
| ② 识票 | OCR 抽取标准字段 + 置信度 | Extractor（Mock OCR 可插拔） | services/ocr.js mock，低置信度人工校对 |
| ③ 归类 | categories.md 启发式 | classifyHeuristic 规则 + 可手改 | utils/categories.js 品类树 |
| ④ 合规 | CoT Stage 5 + policy-template | Compliance Engine（确定性规则 + Vitest） | utils/policy.js 风险前置 + blocked |
| ⑤ 填单 | 生成 `_报销输出/` 报销包 | Claim 状态机 + 汇总四宫格 | 按情景拆单（正式包 / 风险包） |
| ⑥ 审批 | 无（对话内给建议） | 提交 / 通过 / 驳回重提（Mode F） | 无（导出给 HR 验收） |
| ⑦ 交付 | 审批摘要 + 台账 + 合规报告 + 归档 | CSV + 审批摘要 | HR 说明 + CSV + ZIP/manifest |
| 多人角色 | 单会话 | 报销人 / 审批人 | 单用户演示为主 |
| 审计留痕 | processing_log.json | AuditLog 实体 | 思维链「处理依据」可展开 |

**关键一致点**：识别层可错、账本不能错；金额用「分」整数；合规必须可解释；未验真绝不伪称。

## 4. 平台 04 · WorkBuddy Skill（对话出包）

### 4.1 形态与文件

| 路径 | 作用 |
|------|------|
| `极致Prompt-发票报销WorkBuddy.md` | 产品级极致 Prompt（类目/情景/CoT/剧本/质量评分卡） |
| `skills/invoice-reimbursement/SKILL.md` | 可导入 WorkBuddy 的 Skill 主体 |
| `skills/.../references/categories.md` | 类目与票种字典 |
| `skills/.../references/scenarios.md` | Mode A–J 情景路由 |
| `skills/.../references/cot-pipeline.md` | 思维链 Stage Gate |
| `skills/.../references/policy-template.md` | 通用合规基线（可覆盖） |
| `skills/.../scripts/validate_amounts.py` | 金额勾稽与去重脚本示例 |

### 4.2 执行流程（SKILL.md 硬约束）

1. 选模式（默认批量月结 B）
2. 盘点材料 → `processing_manifest.json`
3. 抽取字段（票种/号码/日期/购销方/金额/税额/价税合计/置信度）
4. 去重（号码 → 销售方+日期+价税合计 → 文件哈希）
5. 归类（一级/二级科目 + 场景标签）
6. 合规（`compliant | conditional | non_compliant`）
7. 汇总金额（可提交/待确认/拒报分列；专票进项税单独汇总）
8. 生成产物到 `_报销输出/`：`01-报销单/报销审批摘要.md`、`02-台账/报销明细台账.csv`、`03-合规报告/合规检查报告.md`、`03-合规报告/待确认清单.md`、`04-发票归档/{可提交,待确认,拒报}/`、`05-原始备份/`、`processing_log.json`
9. 归档重命名：`YYYYMMDD_一级科目_销售方简称_金额_发票号后6位.ext`
10. 终检 + 回复（结论 → 风险待办 ≤5 → 产物路径 → 下一步）

### 4.3 启动前必采信息（P0，缺则追问一次 ≤5 项）

1. 报销人姓名/部门 2. 公司抬头（购买方全称）3. 报销归属期间 4. 发票文件或目录路径 5. 制度来源（文件或基线）

### 4.4 质量评分卡（每次交付前写入 processing_log.json）

`field_completeness` · `math_consistency` · `policy_coverage` · `user_questions_needed` · `delivery_ready`
仅当 `delivery_ready=true` 才宣称「可直接提交」，否则说「预览稿/待补齐」。

### 4.5 运行方式

依赖 WorkBuddy 运行时导入 Skill；或把「极致 Prompt」粘贴到 Skill 创建器/自定义专家。无独立可运行仓库，与 05 对照演示。

## 5. 平台 05 · 票易报 Web（审批系统）

### 5.1 技术栈与快速开始

Next.js 15 · TypeScript · Prisma · SQLite · Tailwind CSS 4 · Vitest

```bash
cd 05-projects/05-invoice-reimburse-web
cp .env.example .env
npm install
npm run setup    # prisma generate + db push + seed
npm run dev      # http://localhost:3000
```

| 角色 | 账号 | 密码 |
|------|------|------|
| 报销人 | `lili@demo.com` | `demo123` |
| 审批人 | `manager@demo.com` | `demo123` |

### 5.2 架构

```
[浏览器 Web] 登录 / 工作台 / 报销单详情 / 制度页
        ▼
[Next.js App Router] Route Handlers（auth / claims / invoices / export）
        ├─► Extractor（Mock OCR，可替换真实 Provider）
        ├─► Classifier（类目启发式 + 可手改）
        ├─► Compliance Engine（确定性规则）
        ├─► Pipeline Orchestrator（Stage 0–10）
        └─► Prisma + SQLite（可迁 Postgres）
```

**拆分理由**：识别与合规分离（财务信任来自规则）；金额用「分」整数；Claim 状态机（草稿可改、提交后锁字段、驳回可重提）；Mock OCR 可插拔（无 Key 也能演示）；审批摘要单独导出（服务「1 屏决策」）。

### 5.3 数据模型与状态

**实体**：`User`（employee/manager）· `CompanyProfile`（抬头/税号/简称映射）· `Policy`（酒店限额/招待人均/事前审批阈值）· `Claim` · `Invoice` · `Attachment`（sha256 去重）· `AuditLog`（留痕）

**Claim 状态机**：`draft → submitted → approved | rejected →（Mode F 克隆）→ draft`
- 仅草稿可提交（`仅草稿可提交`）；提交后锁定编辑（`已锁定，不可编辑`）
- 审批必须填原因；驳回后一键克隆为修订草稿，`rejectionReason` 保留「基于驳回单 {id}：…」

**Invoice 字段**：`complianceStatus`（compliant/conditional/non_compliant）· `dedupeStatus`（unique/duplicate）· `riskScore` · `suggestedClaimAmount` · `confidence` · `verificationStatus`（默认 unverified）· `needsUserInputJson`

### 5.4 合规引擎规则（compliance/rules.ts 要点）

- 抬头校验：购买方 ≠ 公司全称/别名 → non_compliant
- 酒店超标：票面价税合计 > 城市档限额 → conditional，建议金额=限额
- 招待：缺人数 → conditional + 待补「招待人数」；人均超标 → conditional，建议=人均上限×人数；≥ 事前审批阈值且无审批证明 → conditional；KTV/高尔夫/夜店 → non_compliant
- 周末大额餐饮（≥¥800）且事由无客户/拜访/加班 → conditional + 风险分
- 同单重复发票号码 → non_compliant + 风险 +30
- 汇总：`totalClaimable / totalPending / totalRejected / totalTax`（四宫格）
- 审批摘要 `buildApprovalSummary`：建议同意 / 建议补齐待确认后再批 / 建议驳回补材料

### 5.5 审批流（角色旅程）

1. 报销人新建（期间/事由/情景模式）→ 上传 → 复核（黄/红状态 + 原因）→ 提交（锁字段）
2. 审批人 1 分钟决策：四宫格金额 → 审批摘要 → 抽查 1–2 张高风险票 → 通过/驳回（必须填原因）
3. 驳回重提（Mode F）：一键克隆 → 只改问题票 → 重提 → 审批人可对照原驳回单
4. 单票速问（Mode A）：「这张餐饮票能不能报？」→ 结论 + 依据 + 建议可报金额

### 5.6 导出与测试

- 导出：CSV + 审批摘要；附件哈希留痕
- 测试：`tests/compliance.test.ts`（金额勾稽、分类、抬头拒绝、酒店超标、招待人均、重复票等黄金样例）
- 种子数据覆盖：酒店超标、招待人均、小票拒报、差旅缺返程提示

## 6. 平台 06 · 票迹小程序（员工收票闭环）

### 6.1 定位（PRD）

| 项 | 内容 |
|----|------|
| 一句话 | 把散落在邮箱和相册里的发票，自动收齐、识别、对上账单，一键生成 HR 能收下的报销包 |
| 形态 | 微信原生小程序（MVP：mail/OCR 默认 mock，可切换 cloud） |
| 成功标准 | 可演示闭环 + Case01–15 + HR 包字段齐全 + 合规可解释 |
| 北极星 | 一次导出通过率 + 人均提交耗时（≤3 分钟 / 10 票内） |
| Must | 邮箱 mock 同步、OCR mock、品类/情景、票账匹配、合规引擎、按情景拆单、HR 导出预览 |
| Won’t（MVP） | 真税务验真生产对接、企微审批流、银企直联、自动换汇、复杂 BI、付费墙 UI |

### 6.2 信息架构

```
Tab：工作台 | 收票箱 | 报销单 | 我的
页：invoice-detail | claim-export
```

首屏预算：品牌 + 待办数 + 同步/拆单 CTA + 最近发票；禁止运营位与统计墙。

### 6.3 主路径与状态机

```
同步邮箱/上传 → OCR/入库 → 分类+情景 → 匹配账单 → 合规扫描
 → 按情景拆单（风险票单独成包）→ ready 导出 HR 包 → 复制说明/CSV
```

- Invoice：`imported → ocr_* → categorized → linked|link_skipped|need_review`
- Claim：`draft → ready|blocked → exported`
- MailAccount：`disconnected → connected → syncing → idle`
- 思维链（详情页可见）：CoT-1 采集 → 2 解析 → 3 验真占位 → 4 分类 → 5 情景 → 6 关联 → 7 合规 → 11 解释（实现：`utils/cot.js`；匹配 `utils/match.js`；合规 `utils/policy.js`）

**异常路径**：重复票 → 同步跳过/标记 duplicate；低置信度 → need_review 阻断 ready；招待超额 → blocked+over_cap；超期 → blocked+overdue；乘机人不一致 → blocked；个人话费抬头 → warn+比例可报；灰色私票 → warn，自动拆单默认剔除。

### 6.4 数据模型与匹配算法

核心实体：`UserProfile · MailAccount · Invoice · Bill · InvoiceBillLink · Trip · Claim · HrPackage · PolicyRule`
存储 Key：`piaoji_state_v1`（wx.storage）

**票账匹配**：
```
score = amount*0.5 + dateWindow*0.3 + merchantSimilarity*0.2
window = travel ? 7天 : 3天
返回 Top3（score ≥ 0.35）
```

**合规优先级**：1. duplicate → 2. low_ocr(<0.85) → 3. title_mismatch / personal_title → 4. over_cap / missing_client / attendees → 5. overdue(>90 天) → 6. passenger_mismatch → 7. private_spend / fx(warn)

**拆单策略（Case15）**：无 error → 按 scenarioMode 生成正式包；有 error → 同情景「待处理风险」包（blocked）；灰色私票默认不进自动包。

### 6.6 验收与案例抽检

验收清单要点：编译通过；同步邮箱入库>0 且重复票跳过；拍照/相册录入可调起相机；详情页风险+匹配+思维链；关联/跳过/校对/补全可用；正式包与风险包分离；ready 可导出、blocked 不可导出；可复制 HR 说明与明细 CSV；无密钥入库。
案例抽检：C01 ready · C02 over_cap · C04 duplicate · C07 overdue · C11 passenger · C13 personal_title。
演示脚本：30 秒（同步→点票关联→拆单→导出复制说明）；2 分钟（+招待拦截+模糊校对+制度页）；5 分钟 HR 视角（核对明细字段与 ZIP 命名）。

### 6.7 上线路径（本地 → 体验版 → 正式）

1. **本地**：微信开发者工具导入 `products/piaoji-mini`；游客 AppID 可自测。注意 `requiredPrivateInfos` 只能填定位类 API，相机/相册走 `permission.scope.camera` + `wx.chooseMedia`。
2. **体验版**：正式 AppID（不进 Git，测试号不能上传）→ 上传 → mp.weixin.qq.com 选为体验版 → 加体验成员 → 发体验版二维码。
3. **正式版**：提交审核（工具/效率或企业类目）→ 发布 → 迭代重传。
4. **Provider 切换规划**：邮箱 mock → OAuth/应用密码+云函数；OCR mock → 腾讯云/自研+置信度；验真占位 → 税务接口；ZIP 预览 → 云函数打包临时链。密钥与 AppSecret 永不进仓。

### 6.8 商业方案（Conditional Go）

**定位**：不做合思级全量费控，做「合思之下、表格之上」的中小团队报销整理层。
**付费方**：50–500 人公司财务/HRBP/办公室负责人；渠道型付费方：代理记账、差旅管家、企微服务商。
**收入排序**：① 企业坐席/年费 ② OCR·验真用量包 ③ 代理记账白标。
**定价假设**：免费个人 ¥0；团队 Starter ¥99–199/人/年（或 ¥15–25/人/月）；团队 Pro ¥299–499/人/年；用量包按次。
**90 天验证（北向只盯 3 个）**：
1. 一次导出通过率 ≥ 75%
2. 人均提交耗时下降 ≥ 40%
3. ≥ 1 家付费或正式 POC

**决策规则**：指标达标+1 家付费 → Go（做企微审批与坐席后台）；通过率↑但无人付费 → Pivot（转代理记账切口/只做差旅包）；无提升 → No-Go（保留技术叙事）。

## 8. 面试 90 秒叙事

> 同一套报销领域能力，我做成了三种载体：Skill 验证 Agent 如何不幻觉乱填金额；Web 验证团队审批与留痕；微信小程序验证员工收票到 HR 包，并给出 Conditional Go 的商业验证计划。我刻意不做合思级中台，先证明一次通过率。

**可讲的产品点（非空泛 AI）**：
- 交付物思维：HR 要的是包，不是识别准确率海报
- 风险前置：入库期拦重复票，比导出期发现便宜
- 可解释：CoT「处理依据」降低黑盒不信任
- 取舍：MVP mock 保障演示，状态机预留 cloud

**深挖优先级**：P0 商业/上线 → 06 · P0 工程运行 → 05 · P1 Prompt 工程 → 04
**避免**：把三款讲成三个无关项目；应强调「同源模型、不同约束下的产品取舍」。

**AI / 平台升级题（有边界）**：票面字段纠错/低置信度辅助 → 可做（人机共审，易评测）；事由/差旅行程自动摘要 → 可做（增效，可失败）；自动替用户提交虚假合规通过 → 严禁（诚信与审计风险）；一次做集团多法人全费控 → 暂缓（范围爆炸）。
